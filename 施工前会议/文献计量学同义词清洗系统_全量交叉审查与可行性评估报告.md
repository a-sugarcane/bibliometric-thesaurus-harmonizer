## 一、总体结论

**这个项目值得做，但只值得先做一个严格受限的 Minimum Viable Experiment（MVE），不值得按现有“完整系统规格”直接开发。**

真实价值不在于“自动生成几个替换文件”，而在于验证：

> 在医学关键词场景中，能否用高精度规则和知识库生成候选映射，在明显减少人工核对时间的同时，不引入具有临床意义的错误合并。

当前材料最大的问题不是软件能否写出来，而是把“检索层面的等价”“严格同义”“临床分析中可以合并”混成了同一件事。**直接将命中同一 MeSH Descriptor 的词自动合并，在方法学上不成立。**

综合判断如下：

- **问题真实存在**：关键词异形、缩写和不透明的人工清洗确实影响可复现性。
- **产品空缺可能存在，但被严重夸大**：现有工具已经提供同义词合并、人工聚类和导入接口；较可信的空缺是“医学知识辅助的候选发现 + 人工审核 + 审计记录”，不是“全球完全没有相关功能”。
- **MeSH 可以使用，但只能是证据源之一，不能直接充当自动合并真值。**
- **现有五阶段流水线过度工程化，且存在严重语义漏洞**：Pass 1/Pass 2 命中 MeSH 后可能绕过风险检查。
- **DAG、Tarjan 破环、势能函数、Worst-Tier 等不是当前验证核心，MVE 中应删除。**
- **15 个工作日可以完成概念验证，但不能可信地完成现有计划中的成熟软件、五类解析器、完整验证、GUI/CLI、软著和正式发布。**

建议：**批准 MVE，暂停完整系统立项。**

## 二、项目全貌

| 问题 | 审查归纳 |

| 项目想解决什么 | 医学文献计量中，同一概念被不同关键词表达，导致共现网络节点分裂；人工合并又可能错误吞并临床亚型。 |

### 2.1 决策演化链

#### 阶段 1：初始方案（2026-09-20）

初始方案采用：

- `desc.xml` 单一数据源；
- 约 15 MB 哈希索引；
- 末位词单复数还原；
- 对称 token 差集拦截；
- 三级置信度；
- 以语料高频词作为规范标签。

对应材料：

- `文献计量学同义词清洗系统_项目开题报告.md`
- `文献计量学同义词清洗系统_可行性分析报告.md`
- `文献计量学同义词清洗系统_用户决策报告.md`
- `文献计量学同义词清洗系统_交接AI技术规格书.md`

#### 阶段 2：审核报告推翻部分旧设计（2026-09-21）

审核报告正确指出五类问题：

1. 缺少 `supp.xml`，可能漏掉药物和化合物；
2. 对称差集会误杀合法缩写；
3. 末位词还原会破坏介词短语；
4. 级联映射可能形成环路和冲突；
5. 简单相加词频与篇级二值计数不一致。

#### 阶段 3：反馈报告再次修正

反馈报告进一步：

- 废弃运行时动态剪枝，改为静态分层索引；
- 放宽缩写证据链；
- 增加 DAG 势能函数；
- 增加词形处理幂等性；
- 形式化双轨频次公式。

#### 阶段 4：实施计划发生范围膨胀

最终实施计划加入：

- PubMed、CNKI、Scopus、VOSviewer 等多种输入；
- 多格式输出；
- GUI 和 CLI；
- DAG 交互编辑；
- 完整软著材料；
- 双人 Git 协作流程。

**关键问题：目前没有一份真正统一的最终规格。**

AI 技术规格书已经被后续报告部分否定；审核报告、反馈报告和实施计划又分别自称“最终”或“唯一”标准，但三者仍然存在冲突。

## 三、独立可行性审查

### 3.1 问题是否真实存在

#### 可以确认的部分

关键词清洗确实是实际问题。相关方法学研究指出，关键词变体、同义词和数据清洗通常需要大量人工参与，而且完全自动生成 thesaurus 的可靠性有限、往往必须针对具体主题制作。

VOSviewer 官方支持两列 `label / replace by` thesaurus，用于同义词、拼写变体和缩写合并，但其主要能力是**执行已有替换表**，不是医学语义自动生成器。

CiteSpace 允许用户交互创建或编辑 `citespace.alias`。

#### 文档夸大的部分

- Bibliometrix 并非“只支持简单正则”。当前版本的 `cocMatrix()`、`biblioNetwork()` 和 `termExtraction()` 已提供 `synonyms` 参数，并支持篇级二值矩阵。
- OpenRefine 不只是简单编辑距离，还提供多种聚类方法、人工批准和外部 reconciliation 服务；但其默认聚类主要是句法层面的，不能替代医学语义判断。
- “90% 研究者依赖 Excel”“全球尚无”“空白蓝海”“刚性需求极强”均缺少可靠市场调查支持。

因此，更准确的市场定位应是：

> 现有工具有规则执行能力，但医学领域高精度候选发现、风险提示和审计体验可能仍不充分。

“全球完全没有同构产品”应标记为：

> 文档内部声称如此，但尚缺外部证据验证。

### 3.2 MeSH 是否适合作为核心知识库

#### 3.2.1 Descriptor ID 不是严格同义词 ID

这是当前最关键的技术问题。

NLM MeSH 的结构为：

```text
Descriptor
  └─ Concept
       └─ Term
```

- **同一个 ConceptUI 下的 Terms 才是严格同义词。**
- 同一个 Descriptor 中可以有多个 Concept，其中一些是更窄概念或相关概念。
- 因此，同一个 DescriptorUI 下的全部 Entry Terms **并不一定严格同义**。

NLM 的官方例子中，`Exercise`、`Aerobic Exercise` 和 `Isometric Exercise` 位于同一 Descriptor record 的不同 Concepts，后两者比前者更窄。将它们全部规范为 `Exercise`，用于热点或前沿分析时会损失研究粒度。

因此，应采用以下判定：

- `same ConceptUI`：可作为强同义证据；
- `same DescriptorUI but different ConceptUI`：只能作为人工审核候选；
- 同一 MeSH Tree 上下位关系：不能当作同义；
- `SCR HeadingMappedTo Descriptor`：不能当作同义。

#### 3.2.2 规格书已经出现具体错误

AI 技术规格书把：

```text
androgen deprivation therapy
→ D000726 Androgen Antagonists
```

写成 MeSH Entry Term 映射。

但 2026 MeSH 的 D000726 Entry Terms 是 `antiandrogen`、`androgen antagonist` 等，并不包含 `androgen deprivation therapy`。

这不是小的拼写错误：ADT 是一种治疗策略，可包含手术去势、GnRH 激动剂/拮抗剂和抗雄激素药物，不等同于“雄激素拮抗剂”药物类别。

这个例子直接说明：现有材料中确实存在未经查证的 AI 技术判断。

#### 3.2.3 Supplementary Concept Record

后期文件正确意识到 SCR 不能通过 `HeadingMappedTo` 吞并进 Descriptor。

但 SCR 不只包含“药物和靶点”。NLM 当前说明其还覆盖化学物、治疗方案、罕见病、微生物和人群等；官方当前统计为超过 23 万条 SCR、超过 50.5 万个 SCR Terms，不是文档所称“30 万条 Supplemental Records”。

合理规则应为：

- SCR 内同一 ConceptUI 的 Terms 可作为别名候选；
- SCR preferred name 可作为显示标签之一；
- `HeadingMappedTo`、Pharmacological Action、Tree parent 只表示关系，不表示等价；
- 药物商品名、通用名、实验编号是否合并，还应由研究问题决定。

#### 3.2.4 MeSH 与文献计量目的存在天然张力

MeSH 为 MEDLINE 的索引和检索设计；文献计量关键词分析经常希望保留作者使用的新词、治疗亚型和前沿表达。

所以：

> “在 PubMed 检索上等价”不能直接推导为“在关键词共现网络中应该成为同一个节点”。

### 3.3 同义词判定逻辑的主要风险

| 类型 | 典型例子 | 风险 |
|---|---|---|
| False Merge | `aerobic exercise → exercise` | 同 Descriptor、不同 Concept，粒度被吞并。 |
| False Merge | `depressive symptoms → major depressive disorder` | 症状不等于正式诊断。 |
| False Merge | `olaparib resistance → olaparib` | 研究对象从耐药机制滑成药物本身。 |
| False Merge | `BRCA1 mutation → BRCA1` | 变异状态、基因和蛋白不是同一分析节点。 |
| False Merge | `androgen deprivation therapy → androgen antagonists` | 治疗策略被缩成药物类别。 |
| False Split | `tumor / tumour` | 英美拼写变体未合并。 |
| False Split | `quality-of-life / quality of life` | 连字符异形未合并。 |
| False Split | `CRPC / castration-resistant prostate cancer` | 只看同篇括号共现会漏掉真实缩写关系。 |
| False Split | 新药商品名与通用名 | 只使用 Descriptor 容易 OOV。 |
| Concept Slippage | `metastatic castration-resistant prostate cancer → prostate cancer` | 前沿亚型被泛癌节点吞没。 |
| Concept Slippage | `treatment-resistant depression → depression` | 治疗反应亚型丢失。 |
| Concept Slippage | `HER2-positive breast cancer → breast cancer` | 生物标志物分型丢失。 |

具体规则判断：

- **单复数**：可以是高精度规则，但不能依赖普遍末尾去 `s`。
- **连字符**：不得在无证据时默认替换为空格；`PD-1`、基因符号、药物编号尤其危险。
- **拼写变体**：英美拼写通常安全，但必须保留原词和规则记录。
- **缩写**：全语料共现只能生成候选，不能“确权”；两个词在某篇文章共同出现不意味着同义。
- **临床限定词清单**：可以作为报警器，但不可能“保证临床安全”。现有清单远不覆盖急慢性、原发/继发、germline/somatic、wild-type/mutant、敏感/耐药等边界。

### 3.4 五阶段流水线审查

| 阶段 | 审查判断 |
|---|---|
| Pass 1：MeSH 整词匹配 | 顺序合理，但“命中即完成规范化”不合理。MeSH 只能生成带 ConceptUI/DescriptorUI 层级的证据。所有映射仍应进入风险检查。 |
| Pass 2：形态/介词规范化 | 可作为候选生成器；“有介词就还原介词前中心词”仍只是启发式规则，不能自动赋予 Tier 1。 |
| Pass 3：风险拦截 | 应覆盖 Pass 1、Pass 2 和缩写生成的全部映射边，而不是只处理前面未命中的词。 |
| Pass 4：DAG/Tier | 当前没有必要。真正的严格同义关系应接近等价类；方向只在最终选择显示词时产生。 |
| Pass 5：传递闭包 | 对混合了严格同义、近义、缩写和人工规则的边做闭包，会放大一次错误。MVE 不应自动闭包。 |

#### DAG 的根本问题

如果 A、B、C 是严格同义，最自然的数据结构是“等价组 + 一个显示标签”，而不是：

```text
A → B → C
```

当前 DAG 很大程度上是在解决前面流水线自己制造的级联映射问题。

反馈报告提出的势能函数：

\[
10^6 I_{\text{Descriptor}} + 10^3 I_{\text{Supp}} + CorpusFreq - 0.1 Length
\]

没有方法学依据，只是一条确定性 tie-breaker。它还与“优先选择语料高频临床词”相冲突：只要是 Descriptor，百万级权重将永远压过语料频次。

Worst-Tier inheritance 也不能解决语义错误。若链中存在 `Blocked` 边，正确处理应是不导出，而不只是把最终边标为高风险。

### 3.5 数据结构与统计口径

反馈报告给出的 `RawSum`、`DocCount`、`Reduction` 公式在数学上基本成立，但它们只解决了一个节点的篇级频次，不能保证整个图谱复现。

VOSviewer 官方说明：

- 对 bibliographic keywords，`Occurrences` 是含有该关键词的文献数；
- 对 bibliographic network，可选择 full 或 fractional counting，影响链接强度；
- 对 title/abstract terms，才另有 binary/full term counting 的区别。

因此：

- `DocCount` 可以重现清洗后关键词节点的 occurrence，前提是输入记录、字段选择和替换规则完全相同；
- `RawSum` 是审计辅助量，不是 VOSviewer 最终节点频次；
- 要重现网络还必须记录数据集版本、DE/ID 选择、阈值、full/fractional counting、时间切片、替换表版本、软件版本和网络参数；
- “双轨频次审计保证可复现”表述过强，最多是可复现性的一部分。

#### DE 与 ID 不应无痕混合

Clarivate 官方定义：

- `DE` 是作者关键词；
- `ID`/Keywords Plus 是从被引文献标题自动生成的索引词。

二者来源和含义不同。当前 `DocumentRecord.keywords: Set[str]` 会丢失字段来源。

MVE 应至少保留：

```text
doc_id
author_keywords_DE
keywords_plus_ID
```

首要分析建议使用 DE；DE+ID 可以作为敏感性分析，而不是默认混为同一套“作者表达”。

### 3.6 工程可行性

#### 合理部分

- Python 适合数据解析和规则实验；
- Streamlit 适合后续人工审核界面原型；
- 本地 MeSH 索引与离线运行方向合理；
- 篇级记录和逐条审计日志值得保留。

#### 不可信或过度设计部分

##### 1. 资源规模

2026 官方文件当前约为：

- `desc2026.gz`：16.8 MB；解压 XML 约 313 MB；
- `supp2026.gz`：47.3 MB；解压 XML 约 786 MB。

因此，“全量双轨 Python JSON/哈希索引、峰值内存不超过 40–45 MB”不可信，除非采用磁盘索引、紧凑二进制表示或明确剪枝。普通 Python `dict` 还会产生显著对象开销。

##### 2. 更新策略

Descriptor 按年更新，但 SCR 为工作日持续更新；“每年 12 月更新一次全部 MeSH”并不完整。

##### 3. 15 天范围

15 天内可以完成单一语料、单一输出的 MVE，但无法同时可靠完成：

- 五类输入格式；
- 全量 MeSH 双轨；
- 临床规则验证；
- DAG 图编辑；
- Streamlit + CLI；
- 三种下游适配；
- gold standard 和外部验证；
- 软著、操作手册、GitHub Release。

##### 4. spaCy 依赖

对只有几千个短关键词的 MVE，spaCy 很可能是过重依赖。它不会自动解决医学概念粒度，而且与“45 MB 峰值内存”目标不协调。

##### 5. 软著代码量导向

国家版权局规定的是鉴别材料通常提交源程序前后各 30 页、每页不少于 50 行；如果整个程序不足 60 页，应提交全部程序。

这不是“软件必须有 3000 行代码”的最低门槛。

因软著而主动把系统扩写到 3800–4500 行，会制造维护成本，甚至削弱原创性说明。

## 四、文档内部矛盾检查

| 问题 | 文档 A 的说法 | 文档 B 的说法 | 是否冲突 | 审查判断 |
|---|---|---|---|---|
| MeSH 数据源 | 规格书只解析 `desc2026.xml` | 审核报告改为 `desc + supp` | 是 | 后期方案覆盖早期方案。 |
| SCR 范围 | 审核称 30 万+ Supplemental Records | NLM 当前为 23 万+ Records、50.5 万+ Terms | 是 | 记录数与术语数混淆。 |
| 索引大小 | 开题/规格称约 15 MB | 反馈称 Descriptor 约 28 MB、总运行内存 40 MB | 是 | 均无实际编译产物和基准。 |
| 动态剪枝 | 审核要求运行时按语料剪枝 | 反馈明确废弃，改静态索引 | 是 | 反馈方案较合理，但性能仍未证实。 |
| 置信度/仲裁层级 | 三级 Tier | 用户报告又称“四级仲裁阶梯” | 表述冲突 | 一个是风险等级，一个是决策顺序，文档未清楚分离。 |
| 缩写 | 规格书中短大写括号词可自动合并 | 审核要求同篇证据；反馈又允许全语料共现 | 是 | 当前应只视为不同强度候选，不应“确权”。 |
| Abstract | 规格目录包含 TI/AB | 用户报告确认当前课题不使用 AB | 是 | 当前 MVE 不应依赖 Abstract 证据。 |
| DE/ID | 用户报告把 DE+ID 作为同一分析集 | 当前数据结构不保存字段来源 | 是 | 必须保留来源并做敏感性分析。 |
| Lemmatization | 规格书只还原末词 | 审核改为 MeSH 优先、介词感知 | 是 | 后者仍须实验验证，不能直接 Tier 1。 |
| DAG | 规格书没有 DAG | 审核/反馈加入 DAG、Tarjan、势能函数 | 是 | 属于后期新增的工程复杂度，尚未证明必要。 |
| canonical term | 用户报告称本地高频表达优先 | 审核称 Descriptor 命名空间绝对优先 | 是 | 必须把“是否合并”和“显示哪个标签”分离。 |
| 势能函数 | Descriptor 权重为 \(10^6\) | 早期称 corpus frequency 决定目标 | 是 | 势能函数实际废除了语料高频优先。 |
| 输入格式 | 规格正文主要支持 WoS/VOS | 实施计划扩张至 WoS/PubMed/CNKI/Scopus/VOS | 是 | 明显范围膨胀。 |
| CiteSpace 格式 | 文档统一声称两列制表符 | 旧版手册曾使用 `#`，当前 FAQ 使用两列 | 版本风险 | 必须针对目标 CiteSpace 版本做真实导入测试。 |
| 代码量 | 反馈各模块最低值相加约 4600 行 | 同表总计写 3800 行 | 是 | 表格自身算术不一致。 |
| “最终标准” | 审核称自己是唯一标准 | 反馈和实施计划又分别称最终/唯一 | 是 | 当前不存在正式合并后的最终规格。 |

## 五、Assumption Register

### 5.1 已有充分依据

- 关键词异形和同义分裂会改变节点及共现网络；
- VOSviewer、CiteSpace、Bibliometrix 均允许用户提供合并规则；
- MeSH 的 Descriptor–Concept–Term 层级真实存在；
- 同 ConceptUI 下 Terms 是比同 DescriptorUI 更强的同义证据；
- 篇级记录是重算节点频次和共现矩阵的必要条件；
- 人工审核与审计记录比“黑箱全自动”更适合此类高风险清洗。

### 5.2 需要验证

- 当前 1570 篇语料中，真正需要合并的词占多少；
- 各规则分别贡献多少正确候选；
- MeSH 对目标语料的覆盖率；
- DE、ID 分开与合并后，主题网络变化多大；
- corpus frequency 是否适合作为显示标签选择规则；
- Streamlit 审核是否真的比 Excel 快；
- VOSviewer、CiteSpace、Bibliometrix 不同版本的导入行为；
- 本地索引实际磁盘、内存和加载时间。

### 5.3 高风险假设

- 同一 Descriptor ID 就适合在关键词图中合并；
- 全语料共现足以解决缩写多义；
- 小规模临床限定词表能够保证“零概念滑坡”；
- MeSH 整词命中可以绕过后续风险审查；
- 混合证据的映射关系可以安全做传递闭包；
- DE 和 ID 可以无差别合并；
- 单一前列腺癌/抑郁语料的结果可以推广到全部医学领域；
- 现有 1489 行人工表可以直接作为 gold standard。

### 5.4 可能是错误结论

- `androgen deprivation therapy = D000726 Androgen Antagonists`；
- “Supplemental Records 超过 30 万条”的当前统计；
- “完整双轨索引约 15 MB、峰值内存 40–45 MB”；
- “软著必须至少有约 3000 行代码”；
- “Bibliometrix 仅支持简单正则替换”；
- “全流程 15 天内达到成熟产品级验收”；
- “90% 以上”“100%”“通过率接近 100%”“完全符合学界规范”等无数据保证；
- “全球尚无、空白蓝海”——目前最多只能说没有找到完全相同的成熟产品，不能证明不存在。

## 六、建议的 Minimum Viable Experiment

### 6.1 核心研究问题

> 与人工表、简单字符串规范化和 MeSH-only 基线相比，概念层级感知的半自动候选生成能否在保持极高 precision 的前提下，将人工审核时间减少至少一半？

### 6.2 第一版只保留的功能

#### 1. 单一输入

WoS 篇级 `savedrecs.txt`，保存：

- `UT/doc_id`；
- `DE`；
- `ID`。

DE 与 ID 不混列。

#### 2. 三类候选生成

- 大小写、空格、明确的标点及英美拼写变体；
- 明确括号缩写和高可信全称候选；
- MeSH ConceptUI 内同义 Terms。

#### 3. 三类候选状态

- `auto-safe`：仅极高精度字符串变体；
- `review`：缩写、MeSH 不同 Concept、SCR 商品名等；
- `do-not-merge`：诊断/症状、亚型、耐药、阶段、药物/靶点等差异。

#### 4. 人工审核表

至少包含：

- 原词；
- 候选目标；
- 证据；
- MeSH ConceptUI；
- MeSH DescriptorUI；
- DE/ID 来源；
- 文献数；
- 接受/拒绝；
- 审核人及备注。

#### 5. 单一输出

第一版只导出：

- VOSviewer thesaurus；
- 审计 CSV/XLSX。

### 6.3 暂时删除的模块

- DAG；
- Tarjan 环路算法；
- 势能函数；
- 传递闭包；
- Worst-Tier inheritance；
- 全量 `supp.xml` 复杂剪枝；
- PubMed/CNKI/Scopus/VOS 聚合解析器；
- CiteSpace/Bibliometrix 专用导出器；
- CLI + Streamlit 双端并行；
- spaCy；
- 软著材料自动生成；
- 为代码行数而进行的模块拆分；
- 15 MB、3.5 秒、45 MB 等未经验证的硬指标。

### 6.4 测试数据

1. 当前 1570 篇前列腺癌与抑郁语料：作为主实验；
2. 第二个不同医学领域语料：建议感染病、心血管或神经病学，用于检查规则是否只适配当前课题；
3. 现有 1489 行人工词表：作为历史对照和候选来源，不能直接视为真值。

### 6.5 Gold standard

最低建议：

- 抽取约 **500 个独立关键词**；
- 覆盖高频词、低频词、缩写、药物、基因、诊断、症状和临床亚型；
- 形成至少 **400 个经过裁决的词对判断**：
  - 约 200 个应合并；
  - 约 200 个 hard negatives，即表面相似但不应合并；
- 两名有医学背景的评审者独立判断；
- 分歧经讨论或第三人裁决；
- 记录 Cohen's kappa 等一致性指标；
- 至少 40% 作为锁定测试集，开发过程中不得反复查看和调规则。

为估计 recall，不能只审核系统已经提出的词对，还需要由人工对抽样关键词建立完整的同义组，并审查一批系统未匹配词。

### 6.6 评价指标

- **Merge precision**：建议合并中真正应合并的比例；
- **False merge rate**：错误合并比例，单独统计临床高风险错误；
- **Recall**：gold 同义关系中系统找到的比例；
- **Review burden**：每 1000 个关键词需要人工判断多少条；
- **Time saved**：与原 Excel 流程相比节省多少时间；
- **Coverage**：多少关键词获得了有效候选或明确状态；
- **下游敏感性**：清洗前、人工 gold、系统结果的 top-20 节点、节点频次和聚类变化；
- **复现性**：相同输入和规则版本能否得到完全相同结果。

### 6.7 进入正式开发的最低门槛

建议同时满足：

- 自动合并 precision ≥ **98%**，且 95% 置信区间下限 ≥ **95%**；
- 锁定测试集中严重临床 false merge 为 **0**；
- 人工审核候选总体 recall ≥ **85%**；
- 相比逐行人工清洗，审核时间减少 ≥ **50%**；
- VOSviewer 受控测试中的清洗后节点 occurrence 与系统 DocCount 完全一致；
- 在第二医学领域 precision 仍 ≥ **95%**；
- 医学评审者认为系统输出解释清楚，而不是增加新的核对负担。

达不到这些指标时，应停留在辅助研究脚本或规则模板，不宜投入完整产品开发。

## 七、风险地图

### P0——正式开发前必须解决

1. 明确“可以合并”的操作性定义：严格同义、检索等价还是分析层级等价；
2. 把 MeSH 匹配从 DescriptorUI 改为 ConceptUI 感知；
3. 修正 ADT 等错误示例，并对现有示例逐条用官方 MeSH 核验；
4. 决定 DE、ID 是否分开分析，并保留字段来源；
5. 建立双人 gold standard 与锁定测试集；
6. 让所有候选映射经过统一风险检查，禁止 Pass 1/2 绕过；
7. 删除“软著需要堆到 3000+ 行”的开发约束；
8. 形成一份真正合并后的权威规格，废止互相冲突的“唯一标准”。

### P1——MVE 中必须验证

- MeSH Concept/SCR 实际覆盖率；
- 缩写候选的 precision 与多义风险；
- 单复数、连字符和拼写规则的错误率；
- corpus frequency 与 MeSH preferred term 的标签选择效果；
- 人工审核节省时间；
- 双轨频次与 VOSviewer 实际导入结果；
- 第二领域泛化性能；
- 用户是否真正需要界面，而不只是审计表。

### P2——后续工程优化

- Streamlit UI；
- CLI；
- Scopus/PubMed/CNKI 支持；
- CiteSpace/Bibliometrix 专用导出；
- SQLite、压缩索引和缓存优化；
- 自动更新 MeSH；
- 多用户协作；
- 软著材料和公开发布；
- 性能压测和安装包。

## 八、项目负责人最需要回答的问题

1. 真正想合并的是“严格同义词”，还是“为了图谱简洁可以视为同一主题的词”？
2. 如果某个更具体的临床概念与大类词在 MeSH 检索中等价，希望保留细粒度还是合并？
3. DE 和 ID 是要混合成一张图，还是分别分析后做敏感性比较？
4. 能否安排两名具有相关医学背景的人独立制作约 400 条 gold 判断？
5. 现有 1489 行人工表由谁制作，是否经过第二人复核，其中可能有多少历史错误？
6. 第一版成功的标准是“找得多”，还是“几乎不发生错误合并”？建议优先后者。
7. 是否接受第一版只输出候选审核表和 VOSviewer 文件，不做完整 GUI、CLI 和多平台支持？
8. 工具只服务前列腺癌与抑郁课题，还是希望推广到所有医学领域？两者所需验证成本完全不同。
9. 如果 MVE 证明只能减少 30% 人工时间、但无法安全自动合并，“人工审核助手”是否仍具有产品价值？

## 九、最终建议

### 立项判断

**有条件值得做。**

项目真实可成立的定位是：

> 面向医学文献计量的高精度、可审计、人工在环的关键词规范化候选与审核工具。

当前不成立或尚未被证明的定位是：

> 基于 MeSH 即可自动、全面、安全、通用于所有医学领域的同义词清洗系统。

### 建议决策

1. 暂停执行现有 AI 技术规格书和双人完整实施计划；
2. 先修复 MeSH 语义模型与 DE/ID 数据模型；
3. 建立 gold standard；
4. 完成窄范围 MVE；
5. 只有达到预设 precision、false merge、recall 和节省时间门槛后，才进入正式软件开发；
6. 将软著、GUI、多格式和性能优化放在概念验证之后。
