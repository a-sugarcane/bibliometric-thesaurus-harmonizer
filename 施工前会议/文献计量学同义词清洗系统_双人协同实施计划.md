## 一、 总体技术架构与基准规范

本实施计划严格贯彻五阶段确定性流水线，确保医学专科准确性与抗同行评审质询能力：

```
[原始题录/词表]
      │
      ▼
┌─────────────┐   未命中   ┌─────────────┐   未命中   ┌─────────────┐
│   Pass 1    │ ─────────► │   Pass 2    │ ─────────► │   Pass 3    │
│ MeSH整词查表 │            │ 介词感知还原 │            │ 语境与差集  │
│ (Desc+Supp) │            │ +二遍回溯   │            │ 风险拦截器  │

      │                          │                          │
      └──────────┬───────────────┴──────────────────────────┘
                 │ 候选映射边 (带初始 Tier 标记)
                 ▼
          ┌─────────────┐
          │   Pass 4    │ ◄─── 用户在 Streamlit 界面交互微调

                 │ 确认导出触发

          │   Pass 5    │ ───► VOSviewer (thesaurus.txt)

          │ 与多格式导出│ ───► Bibliometrix (synonyms.csv)
          └─────────────┘ ───► 期刊补充材料 (双轨频次审计表.xlsx)
```

### 核心算法防御性约束
1. **知识库双轨静态索引**：`desc2026`（核心主题词）与 `supp2026`（小分子/药物/靶点）独立预编译为静态 JSON，严禁按 `<HeadingMappedTo>` 粗暴归类。
2. **三级缩写置信度**：同篇显式括号（Tier 1）$\to$ 全语料共现对齐（Tier 2）$\to$ 孤立多义词拦截（Tier 3）。
3. **介词感知中心词还原**：全词 MeSH 匹配绝对前置；仅在未命中时对介词（`in`, `of`, `with`）前置词还原，确保幂等性。
4. **DAG 势能破环与木桶继承**：按势能函数 $\Phi(v)$ 选取唯一绝对汇点，压缩路径强制继承路径最高风险级别。
5. **自适应双轨频次审计**：篇章级源输出 `Raw Occurrence Sum` 与 `Document Independent Count`；聚合源显式标注 `N/A` 并附带方法学合规条款。

## 四、 GitHub 多人协同作业规范与防冲突纪律（SOP）

为杜绝协同过程中的代码覆盖、分支冲突与灾难性提交，制定以下四项硬性纪律：

```
                ┌────────────────────────────────────────────────────────┐
                │          GitHub 极简无冲突协同工作流                   │
                └────────────────────────────────────────────────────────┘
                                             │
      ┌──────────────────────────────────────┴──────────────────────────────────────┐
      ▼                                                                             ▼
【成员 A 工作流】                                                             【成员 B 工作流】
git checkout main                                                             git checkout main
git pull origin main                                                          git pull origin main
git checkout -b feat/A-ontology-dual                                          git checkout -b feat/B-parsers-multi
        │                                                                             │
  让 AI 在 core/ontology 下编码                                                 让 AI 在 core/parsers 下编码
  并运行 test_ontology.py                                                       并运行 test_parsers.py
        │                                                                             │
git commit & git push                                                         git commit & git push
在 GitHub 发起 PR #1                                                          在 GitHub 发起 PR #2
        │                                                                             │
由成员 B 审查点击 Merge                                                       由成员 A 审查点击 Merge
```

### 1. 分支命名与物理隔离规范
- 严禁任何人直接向 `main` 分支执行 `git commit` 或 `git push`。
- 分支命名严格绑定角色与工单号：
  - 成员 A 的特性分支：`feat/A-mesh-supp`、`feat/A-dag-resolver`
  - 成员 B 的特性分支：`feat/B-parsers-update`、`feat/B-ui-aggrid`

### 2. 每日编码前置动作（Pull before Work）
- 每天开始让 AI 编写代码前，第一条命令必须拉取最新主分支代码：
  ```bash
  git checkout main
  git pull origin main
  git checkout -b feat/你的分支名
  ```

### 3. Pull Request (PR) 审查与合并契约
- 任何代码并入 `main`，必须在 GitHub 网页端提交 Pull Request。
- **交叉审查制度**：成员 A 发起的 PR 必须由成员 B 点击 Merge；成员 B 发起的 PR 必须由成员 A 点击 Merge。
- **PR 提交前自查清单**：
  - [ ] 对应模块的代码是否均在自己负责的排他性目录内？
  - [ ] 本地运行 `python3 -m unittest discover -s tests` 是否 100% 通过？
  - [ ] 是否包含多余的临时日志或未加入 `.gitignore` 的大文件？

### 4. 冲突紧急避险对策
- 若偶发 Git Merge Conflict（冲突）：
  - 严禁强行使用 `git push -f`（强制推送）；
  - 立即在终端执行 `git merge --abort` 撤销合并，呼叫搭档比对重叠文件的行数，由负责该文件的独占成员在分支内修改后再提 PR。

## 五、 接口协议与数据交付物契约

### 1. 篇级记录接口（Parsers $\to$ Pipeline）
```python
@dataclass
class DocumentRecord:
    doc_id: str                          # 文献唯一标识 (UT/PMID/DOI/TitleHash)
    keywords: Set[str]                   # 该篇文献内的全部原始关键词集合 (用于二值去重)
    source_database: str                 # 数据库来源 (WoS/PubMed/CNKI/Scopus/VOS)
    is_aggregated_source: bool = False   # 是否为无篇章信息的预聚合词频源
```

### 2. 规则产出接口（Decision Engine $\to$ Exporters）
```python
@dataclass
class HarmonizationRule:
    raw_term: str                        # 原始脏词
    target_term: str                     # 规范目标词
    tier: str                            # 置信层级: Tier 1 / Tier 2 / Tier 3
    rule_source: str                     # 规则来源: MeSH (ID) / Lemmatization / Acronym
    clinical_safety_check: str           # 临床安全状态: Passed / Blocked: High-Risk
    raw_sum_occurrences: int             # 原始出现总频次和 (Raw Sum)
    document_independent_count: int      # 篇级独立去重文献数 (Doc Count, 聚合源为 -1)
    cooccurrence_reduction: int          # 同篇被布尔去重的频次
    selected_for_export: bool = True     # 用户是否勾选导出
```

## 六、 成员 A 与成员 B 的六大关键协同对接节点（Joint Junction Protocols）

在两人的物理隔离开发模型中，最容易因“各自向 AI 提问产生理解偏差”而导致系统断裂的地方正是**模块交界处的协议契约**。整个研发周期中，A、B 两位成员必须**面对面（或屏幕共享）共同确认代码签名并完成联调对接**的关键节点共有 6 处：

### 节点 1（第 3 天）：数据流入口契约对接（`DocumentRecord`）
* **对接阶段**：第一阶段收尾（里程碑 1）
* **涉及接口**：`project/core/parsers/base_parser.py` $\leftrightarrow$ `project/core/engine/`
* **对接核心任务**：
  - 成员 B 交付的数据结构必须严格满足 `DocumentRecord` 定义；
  - 成员 A 验证对于预聚合输入源（VOSviewer TSV），`is_aggregated_source == True` 标记能被下游正确感知，确保频次统计不发生空指针异常。
* **验收裁判**：成员 B 提供一段包含 5 篇 WoS 和 1 份 VOS TSV 的微型测试集，成员 A 的管道解析成功并断言字段类型 100% 合规。

### 节点 2（第 6~7 天）：缩写语料证据链与共现索引对接（`CorpusContext`）
* **对接阶段**：第二阶段收尾（里程碑 2）
* **涉及接口**：`project/core/parsers/` $\leftrightarrow$ `project/core/interceptor/risk_rules.py`
* **对接核心任务**：
  - 为避免成员 A 清洗时反复遍历全量题录，成员 B 在解析阶段构建反向共现查询助手：
    ```python
    class CorpusContext:
        def has_cooccurrence(self, term_a: str, term_b: str) -> bool:
            """查询 term_a 与 term_b 是否至少在某一篇文献中共同出现过"""
    ```
